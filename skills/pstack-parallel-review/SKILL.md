# pstack 平行審查與競技（濃縮版）

> 來源：`cursor/plugins` 的 `pstack`（作者 Lauren Tan，MIT）。本檔為方法論的濃縮重述，非原文複製。原始專案：https://github.com/cursor/plugins/tree/main/pstack 。完整授權見同目錄 `ATTRIBUTION.md`。

## 何時用

| 情境 | 用哪個 |
|------|--------|
| 不同切片要同時覆蓋（例如每個套件跑一次檢查） | swarm |
| 同一任務要多種做法競技、取出最強部分 | arena |
| 有人對設計或 diff 有爭議，要找出真正會壞的地方 | interrogate |

**所有平行操作仍由主理人統籌**（ TeamCreate → 調度 → 回傳 → 彙編），不改變本團隊的協作铁律。_worker 之間不得直連_，各自獨立輸出路徑，由主理人合併。

## Swarm — 分割／競速，最後一份報告

四階段先寫進任務清單再啟動：Frame → Fan out → Aggregate → Report。

1. **Frame**：寫下完成判準與要回傳的產物。選形狀：分割切片、相同 brief 競速、或混合；競速要**先宣告** `first pass`／`rank all`／`best-of`。給每個 worker 獨立可寫的輸出路徑；驗證或量測 commit 時，brief 要寫明確切 SHA，量測還要寫明方法（樣本數、什麼算一個樣本、順序）。
2. **Fan out**：一次訊息中派出全部 worker。每份 brief 自成完整单元：目標、範圍、確切切片或競速手臂、如何驗證、要回報什麼。回報用 `PASS`／`ISSUES`／`BLOCKED` 並附證據；能證明缺陷就列全部可證明問題，不只第一個。有人掉線就用 N-1 繼續並註記。
3. **Aggregate**：丟掉沒有記錄 SHA 與方法的結果，並重派一次；第二次仍缺就記為 gap，**gap 不算通過**。覆蓋型任務每個切片都要有結果；競速型套用事先宣告的規則。不要貼原始 dump。
4. **Report**：一份整合報告，含結果表、問題摘要、gap 與掉線、使用的競速規則。

## Arena — 多家提案，選基底，移植強項

六階段先寫進任務清單：Frame → Fan out → Cross-judge → Pick → Graft → Verify。

1. **Frame**：所有候選收到**相同的 prompt**（prompt 就是契約）。另外私下備好 3–6 條可評分的驗收準則（候選看不到）。每個候選給獨立輸出路徑（git worktree 或 `/tmp/arena-<slug>/candidate-<n>/`），避免共享寫入。
2. **Fan out**：同時派出；每份要求產出成品＋簡短理由（考量過哪些替代、為什麼否決）。沒產生的就 N-1 並註記。
3. **Cross-judge**：找一位**不使用同源模型**的唯讀評審，按路徑標籤逐條準則打分並推薦基底。主理人不知道父模型時就略過這一步並明說。
4. **Pick**：先完整讀完每個候選，再逐條準則對照評分，不靠整體感覺。選「未來維護者最容易在不破壞 invariant 下擴充」的那個；難分高下時選邊界更乾淨、API 更小者。與 cross-judge 不一致時，讀雙方理由再決定（代表有偏見或準則太模糊）。
5. **Graft**：把落選者再走一遍，通常每個只移植一兩處。手動整合，保持在單一心智模型下連貫，不機械貼上。若候選收斂到同一形狀，那是強共識，直接出貨；若差異極大，代表 Frame 寫得不夠，重寫重跑，不要平均。
6. **Verify**：對合成結果完整驗證。若驗證抓到 arena 沒抓到的問題，要嘛 Frame 錯（重寫重跑），要嘛移植漏了（回 Graft），不得補漏洞帶過。

**輸出**：合成成品＋綜合說明（基底為何、cross-judge 裁決、每處移植的來源、否決了什麼、收斂或掉線、驗證結果）。

## Interrogate — 對抗式審查，只留跑過的發現

目的在「找出會壞的地方」，**不做修復**。

1. **Frame**：界定範圍（使用者指定的，或分支相對 base 的 diff 含工作區變更），並由瑞克依使用者訊息、commit、PR 描述復述意圖；意圖不清就問使用者。
2. **Fan out**：每位對抗者拿到範圍、意圖與同一個 brief：「設法破壞這個變更。每個發現都要用真實程式上的一次執行證明（失敗測試、重現腳本、顯示錯誤行為的指令輸出）。設計或計畫就用原型或探測現有程式。每個發現寫標題、確切指令、實際輸出、意圖要求的輸出。沒跑過的一律不寫（含風格、命名、結構、需要未來變更才重要的風險）。沒有發現也是有效結果。」
3. **Verify**：主理人重跑每個發現的指令。只有輸出確實顯示失敗且該失敗破壞意圖才保留；其餘丟棄。共享根因的發現合併。蒐集**所有**通過驗證的發現，不是只留某一位的清單。

**輸出**：意圖復述、每個通過驗證的發現（指令、輸出、如何破壞意圖、誰找到的）、每位對抗者被丟棄的數量與原因；沒有就寫「無通過驗證的發現」。

## 委派紀律

- 大量輸出交給 worker，主執行緒只留摘要（守護上下文視窗）
- 同一個修復輪次、追問或重試，優先派**新的** worker 並帶原始 brief＋所有後續指令＋前一位的報告與分支；只有狀態確實難以搬移（未提交變更、仍在跑的 process）才續用
- 你擁有每個 worker 的產出：親自看 diff、自己寫總結
- 第二意見 = 同一份 prompt 換不同模型，不是換個說法再問一次
