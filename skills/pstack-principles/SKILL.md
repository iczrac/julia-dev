# pstack 工程原則（濃縮版）

> 來源：`cursor/plugins` 的 `pstack`（作者 Lauren Tan，MIT）。本檔為方法論的濃縮重述，非原文複製。原始專案：https://github.com/cursor/plugins/tree/main/pstack 。完整授權見同目錄 `ATTRIBUTION.md`。

## 何時用

由主理人在 Phase 0 指定，或任何成員在寫程式、審查、重構、驗證時自行套用。**不是流程，是判斷標準**——它回答「怎樣才算把這件事做好」。

與其他 Skill 的關係：`pstack-playbooks` 管「先做什麼、後做什麼」，本 Skill 管「每一步的取捨標準」；`pstack-verification` 是其中驗證類原則的展開。

## 使用紀律

1. 回報時**點名影響決定的原則**，並說清楚它改變了哪個具體選擇。只寫「遵循最佳實踐」不算。
2. 原則衝突時，優先順序：硬門禁（人工確認、Vera `PASS`、OKF 溯源）> 驗證類原則 > 架構類原則 > 核心類原則。
3. 同一條原則被口頭重複第二次，就該把它寫進結構（lint、型別、檢查腳本），而不是再寫一次文件。

## 五組二十四條

### 核心（寫任何程式碼前）

| 原則 | 何時套用 | 規則 |
|------|----------|------|
| 惰性協定 Laziness Protocol | 重構、控制 diff 大小、想加抽象層時 | 偏好刪除；只做能解決問題的最小變更 |
| 基礎思維 Foundational Thinking | 寫邏輯之前 | 先定核心型別與資料結構、腳手架與功能順序、並行行為共享什麼。資料結構對了，下游程式自然清楚 |
| 從第一性原理重新設計 | 新需求要塞進舊設計 | 假設需求一開始就是基礎假設，重新設計，不要外掛 |
| 攻擊前提 Attack the Premise | 兩個以上共享同一前提的修法都過不了同一關 | 把前提寫下來直接驗證，別再寫第三個假設它的修法 |
| 先減後加 Subtract Before You Add | 新增、重構、改寫的排序 | 先清掉死程式、重複校驗、殘留引用，再在更簡單的基礎上加 |
| 最小化讀者負擔 | 程式碼難以追蹤時 | 數一數從問題到答案跨幾層、讀者腦中藏多少狀態；合併只有一個呼叫者的包裝、縮小可變範圍 |
| 結果導向執行 | 有明確階段邊界的改寫與遷移 | 收斂到目標架構，不要用 throwaway 相容層維持平滑中間態 |
| 體驗優先 | 產品、UX、功能範圍取捨 | 選使用者驚喜，而非實作方便；少而精勝多而糙 |
| 窮盡設計空間 | 沒有前例的互動或架構決策 | 做 2–3 個競爭原型並排比較後再定案 |
| 造槓桿 Build the Lever | 任何非瑣碎工作 | 做工具（codemod、腳本、生成器、讓 subagent 遵循的 Skill）來做或證明，別手工硬做；工具才是審查者可重跑的產物 |

### 架構

| 原則 | 規則 |
|------|------|
| 建模領域 Model the Domain | 把領域編成結構（狀態機、型別模型、表或註冊表、reducer、邊界、合適的集合），不要散落成條件判斷 |
| 邊界紀律 Boundary Discipline | 校驗與錯誤處理集中在系統邊界（CLI、設定、網路、外部 API）；信任內部型別，商業邏輯留在純函式 |
| 型別系統紀律 | 讓非法狀態無法被表達；為語意基本型別做品牌化；外部資料在邊界解析；窮盡所有 variant；從權威 schema 推導 |
| 操作冪等 | 崩潰與重試後收斂到相同終態 |
| 先遷移呼叫端再刪舊 API | 同一波遷移呼叫端並刪除舊 API，不留相容層 |
| 先分離再序列化共享狀態 | 併行行為可能寫同一檔案／分支／鍵時，先消除共享；只有真 invariant 才序列化 |

### 驗證

| 原則 | 規則 |
|------|------|
| 證明它可行 Prove It Works | 宣告完成前，針對真實產物驗證（跑功能、讀實際值、看 diff），不是代理指標、自我回報或「能編譯」 |
| 修根因 | 從症狀追到系統第一次出錯的地方並在那裡修。guard 只有在它處理的狀態是合法時才算修復 |
| 切成可驗證單元 | 多步驟工作拆成每個都以檢查收尾的小單元，逐個驗證再往下；交付順序要能自我證明 |
| 測行為不測實作 | 測試宣告使用者可觀察的結果：行為壞就失敗，內部改寫仍通過 |
| 解釋數字 Explain the Number | 信任、報告或依據某數字行動前，找出是什麼在限制它，排除它量的不是你以為的東西 |

### 委派

| 原則 | 規則 |
|------|------|
| 守護上下文視窗 | 大量輸出交給 subagent，主執行緒只留摘要，不塞原始 payload |
| 不阻塞人類（**受本團隊門禁限制**） | 可逆工作直接做、做完再報告；**但** Workflow L 的人工確認、不可逆寫入與Vera `PASS` 門禁優先於本原則 |

### 後設

| 原則 | 規則 |
|------|------|
| 把教訓編進結構 | 重複第二次的規則改成 lint、metadata flag、runtime check 或腳本，不要再寫一段文字 |

## 與本團隊既有能力的對應

- 「建模領域」「邊界紀律」與 `ontology-modeling` 的語語義邊界互補：後者管跨模型職責，本 Skill 管單一程式碼邊界。
- 「證明它可行」「修根因」「解釋數字」的完整操作見 `pstack-verification`。
- 「窮盡設計空間」需要並行原型時，見 `pstack-parallel-review` 的 arena。
