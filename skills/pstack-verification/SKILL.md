# pstack 可驗證性方法（濃縮版）

> 來源：`cursor/plugins` 的 `pstack`（作者 Lauren Tan，MIT）。本檔為方法論的濃縮重述，非原文複製。原始專案：https://github.com/cursor/plugins/tree/main/pstack 。完整授權見同目錄 `ATTRIBUTION.md`。

## 何時用

由維拉（QA）主導，在 Phase 4 與所有「宣稱完成」的時刻使用。這是對既有 `PASS/FAIL` 紀律的**操作化升級**：從「人工判定有無證據」變成「證據必須怎麼取得、怎麼核對」。

與既有 Skill 的關係：`ontology-modeling` 的追溯門禁查「需求到程式碼的對應」，本 Skill 查「程式實際跑起來的行為」；OKF 的 attestation 查「計算回執是否被竄改」，本 Skill 查「數字是怎麼量出來的」。三者互補，不可互相替代。

## 一、證明它可行（Prove It Works）

宣告完成前，針對**真實產物**驗證：

- 跑功能、讀實際值、檢查 diff — 不是「能編譯」、不是代理指標、不是作者的自我回報
- 「inconclusive」或驗證在錯誤介面（例如只在 API 測 UI 行為）不算通過，必須明確標註
- 捕獲動作與其造成的狀態變化，不能只拍最終画面；同時驗證副作用（檔案寫入、資料列新增、訊息送出）
- 清理掉驗證過程建立的實例，但**證據要留下**在指定的位置

## 二、基準檢驗七問（Explain the Number）

任何速度、延遲、吞吐量、 regression 或 eval 數字，在報告或據以行動前逐項回答，每項都要有執行證據：

1. **為什麼沒有翻倍？** 說出限制因子。用不列入報告的一次 profiling 找熱點，並檢查負載產生器是否先飽和（那時你量的是產生器）。
2. **調過參數嗎？** 每一邊都按生產方式跑（release build、生產旗標、批次與交易設定、連線池、快取冷熱、相同版本與資料）。一邊用預設值，比的是設定不是實作；調不了就不要從那次結果選贏家。
3. **算得過去嗎？** 做數量級算術：移除只佔 10% 的部分，最多快約 11%。超過物理上限的結果量到的是別的東西（快取、no-op、bug）。
4. **有錯誤嗎？** 計數失敗与非成功回應，並確認輸出正確。拒絕通常很快，超時與重試很慢。
5. **能重現嗎？** 每邊至少 5 次，交替執行（A,B,A,B…），讓 warmup 與快取不偏向任一方。報告中位數與區間；差距小於抖動就是無可量測差異。
6. **重要嗎？** 微觀數字旁邊要量端到端使用者等待的路徑，並報告微觀結果佔比。
7. **真的發生了嗎？** 確認工作在執行計時区间内：請求到達、資料列寫入、位元組讀出、結果被使用。惰性求值、沒人 await 的 promise、超時會量到沒發生的工作。

**報告格式**：先給裁決（更快／更慢／無可量測差異／inconclusive），再給數字＋單位＋執行次數＋區間＋限制因子。無法說出限制因子、某一邊未調校、或無法檢查第 4／7 題時，裁決必須是 inconclusive。

## 三、建立專案本地驗證 Skill

適合「專案沒有腳本化方式證明行為」時。維拉可指示麥克或席普產出，自己負責驗收。

**先問 repo，不要問使用者**（問不到才問人）：使用者實際碰到什麼介面（web UI／CLI／API／桌面／行動）、本機怎麼啟動、agent 如何程式化驅動、能捕獲什麼證據、兩個實例能否並存（不能就明說，拒絕共用實例）。

生成的 Skill 必須包含：

| 段落 | 要求 |
|------|------|
| Launch | 精確啟動指令與「ready」判準（可用，不只是 process 活著）；從空資料目錄可達可用狀態，含 migration 與 seed；含 teardown |
| Doctor | 一個唯讀檢查回答「這個實例值得驅動嗎」 |
| Drive | 真實 selectors／指令，偏好穩定 handle（ARIA label、data attribute、route），不要座標與 tab 順序 |
| Evidence | 證據標準與存放位置；走真使用者路徑，不用內部 setter 或測試專用端點；mock 僅限生產邊界已隔離外部系統處；dry-run 要實際觀察它跳過了什麼 |
| Cleanup | 只殺自己啟動的進程，不按名稱砍；清理實例与暂存，不清理證據 |
| Helpers | 每個腳本可執行，呼叫方式寫在正文 |

**功能地圖**：README 索引＋每個使用者可見功能一份檔案（先 3–5 個），每份從使用者視角回答「功能是什麼／怎麼到達／怎麼驅動／什麼可觀察終態證明它可用」。缺少前置資料的旅程要回報失敗並記在 Gotchas，**不可為了通過而弱化旅程**。

**交付前先自己跑一遍**：launch → doctor → 驅動一個功能 → 捕獲證據 → cleanup → 確認證據還在。沒跑過的驗證 Skill 是草稿，不是交付物。用替代環境驗證過的，要列出替代環境做過而目標環境不會做的每一步。

## 四、形式化驗證（測試到不了的地方）

適用：競態、重試、狀態機、解析器、unsafe code 等「測試很少碰到、壞了很痛」的承諾。

1. **從程式碼選目標**：選最強的承諾，不是最容易驗證的那個。
2. **讓問題選工具**：事件順序 → model checker（小模型，預設 TLA+）；程式本身對所有輸入的行為 → 跑在程式上的 verifier；語言沒有 verifier 就明說，改用以生成輸入測真實程式，不要用手工模型冒充。
3. **好驗證的標準**：模型每部分都指向可打開的程式碼；**必須看過它失敗**（在故意破壞的變體上展示失敗）；發現就是發現，不為了通過而弱化 property；誠實說明邊界與假設；一句話講清 property 與傷害；一鍵重跑；記錄覆蓋檔案與上次確認的 commit。
4. **交付前同樣自測**：在真實程式上做一個破壞 property 的臨時變更，驗證必須抓到，然後還原並確認回到原狀態。
5. **漂移處理**：被覆蓋的程式碼在同步 commit 之後改變時，下一次驗證必須重新確認，而不是直接沿用舊結論。

## 五、把錯誤釘死在結構裡（Correct）

使用者反覆糾正的同一類錯誤，依序嘗試最高層級的修法：

1. 架構消除（狀態單一 owner、每件任務只有一種支援做法、隱藏內部讓錯誤 import 直接失敗）
2. 型別讓壞狀態寫不出來；壞程式還能編譯就加 lint／CI，且錯誤訊息要指名該改用哪個檔案、型別或函式
3. 測試行為（會因為行為壞掉而失敗、只改內部仍通過）
4. 文件與 agent 規則放最後，只處理判斷題

每一類都要用真實歷史錯誤證明新檢查會失敗；例外寫在犯規行並附原因、到期日與人工核准。
